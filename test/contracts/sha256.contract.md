## 1. Domain contract

### Objects

- **Bit** = `Bool`. **Bit string** = `List Bool`, arbitrary finite length, in
  the FIPS 180-4 ordering fixed by §3.1.
- **Word** = `BitVec 32`. FIPS 180-4 §4.1.2 defines every logical function on
  32-bit words, and §3.1 fixes the big-endian reading of a word.
- **Byte string** = `List UInt8`. This is the carrier of the byte-level
  reference `Sha256.Impl` and of every known-answer test.
- **`ByteArray`** is not an object of this contract. It belongs to the native
  layer `Sha256.Fast` (§4 A1.S4) and to the public API (§4 A1.S3), and enters
  the claim path only through `Fast.sha256_eq_impl`.
- **State** = `Vector Word 8`; **block** = `Vector Word 16`; **schedule** =
  `Vector Word 64`. Sizes are carried by the type, so no length side
  condition is needed on any round lemma.

### Operations

All total, all terminating without fuel, none partial. The names are the
frozen ones of `docs/SHA256-DAG.md` §4 A1.S1; this contract introduces none.

*Bit-level transcription, `Sha256.Spec`.* `Ch`, `Maj` (§4.1.2 equations 4.2,
4.3); `Σ0`, `Σ1`, `σ0`, `σ1` (§4.1.2 equations 4.4–4.7); `K : Vector Word 64`
(§4.2.2); `H0 : Vector Word 8` (§5.3.3); `pad : List Bool → List Bool`
(§5.1.1); `parse : List Bool → List (Vector Word 16)` (§5.2.1);
`schedule : Vector Word 16 → Vector Word 64` (§6.2.2 step 1);
`compress : Vector Word 8 → Vector Word 16 → Vector Word 8` (§6.2.2 steps
2–4); `hash`; `bitsOfWords` (§3.1, big-endian, most significant bit first);
`sha256 : List Bool → List Bool`; `bitsOfBytes` / `bytesOfBits` (§3.1);
`sha256_bytes`.

*Byte-level reference, `Sha256.Impl`.* `padBytes`, `wordOfBytes`,
`wordsOfBlock`, `schedule`, `compress`, `blocks`, `hash`, `bytesOfWord`,
`sha256`. `Impl` shares `Spec`'s `Ch`, `Maj`, `Σ0`, `Σ1`, `σ0`, `σ1`, `K` and
`H0` directly rather than restating them: the two layers differ only in how
bytes become words and how blocks are cut, which is what makes the bridge a
data-flow proof rather than an arithmetic one.

`Spec.parse` and `Spec.hash` are total extensions. They carry FIPS 180-4
meaning only on padded input; on unpadded input they are defined and
meaningless. Nothing in this contract claims otherwise.

### Observables and equivalence

The only observable is the output byte string, or its bit string at the
`Spec` layer. Equality is propositional equality of outputs. There is no
observation mask, no timing observable, and no intermediate state is
observable: `compress` is compared only through the digest it contributes to,
except where a frozen lemma names it directly.

Refinement is extensional and runs in one direction at each layer:
`Impl.sha256 msg = Spec.sha256_bytes msg` on byte strings (§4 A1.S2
`Bridge.sha256_bridge`), and
`(Fast.sha256 bs).data.toList = Impl.sha256 bs.data.toList` (§4 A1.S4
`Fast.sha256_eq_impl`).

### Scope

**IN.** SHA-256 over byte-aligned messages: the §4.1.2 word functions, the
§4.2.2 constants, the §5.3.3 initial value, §5.1.1 padding, §5.2.1 parsing,
the §6.2.2 hash computation, §3.1 bit and byte ordering, the pinned CAVP
short-message vectors, and the two refinements above. SHA-224 enters at S1.6
as the discriminating negative's positive twin.

**OUT, explicitly.** Security properties of any kind — collision resistance,
preimage resistance, indifferentiability, length-extension behaviour. The
hash's injectivity. Conformance beyond the pinned vectors. Performance as a
theorem; every timing number in this lane is a measurement and is reported as
one. Bit-level, non-byte-aligned messages at the executable layer. The
`Msg`/`Len` pairs of the CAVP long-message file. SHA-384, SHA-512,
SHA-512/224, SHA-512/256, HMAC, HKDF. Streaming (S1.5, after the bridge).

### Forbidden example (the discriminating negative)

**SHA-224 is not SHA-256 truncated, and SHA-256 with the SHA-224 initial
value is not SHA-224 either.** FIPS 180-4 §6.3 states that SHA-224 is defined
in the exact same manner as SHA-256 with exactly two exceptions: the initial
hash value comes from §5.3.2, and the final hash value is truncated to its
left-most 224 bits. The two initial values differ in all eight words:

| | §5.3.3 SHA-256 | §5.3.2 SHA-224 |
| --- | --- | --- |
| H₀ | `6a09e667` | `c1059ed8` |
| H₁ | `bb67ae85` | `367cd507` |
| H₂ | `3c6ef372` | `3070dd17` |
| H₃ | `a54ff53a` | `f70e5939` |
| H₄ | `510e527f` | `ffc00b31` |
| H₅ | `9b05688c` | `68581511` |
| H₆ | `1f83d9ab` | `64f98fa7` |
| H₇ | `5be0cd19` | `befa4fa4` |

The initial value is load-bearing and nothing else in the algorithm reveals a
mistake in it: a transcription that used the §5.3.2 words would satisfy every
structural theorem in §4 A1.S1 — every length lemma, every padding lemma,
every round identity — and produce a wrong digest for every input. The
negative pins it. Its S1.2 form is stated on `Spec.H0 ≠ sha224IV` by `decide`;
its final form is `Bridge.sha256_ne_sha224_iv` at S1.6, when `Impl.hashWith`
exists. **Injectivity of `compress` is not claimed** in either form, and the
negative does not need it: it is a statement about two named constants and
the digests they produce on a named input, not about the round function.

A second, weaker negative is available at no cost and should be taken: the
constants of §4.2.2 are the cube roots of the first sixty-four primes and
those of §5.3.3 are the *square* roots of the first eight, so `K[0]` and
`H0[0]` are unrelated; a transcription that seeded `H0` from the `K` table's
head would be caught by W1 alone.

### Edge cases

- **E1 — the last length whose padding fits one block.** `Len = 440`, 55
  bytes. `Msg`
  `3ebfb06db8c38d5ba037f1363e118550aad94606e26835a01af05078533cc25f2f39573c04b632f62f68c294ab31f2a3e2a1a0d8c2be51`,
  `MD` `6595a2ef537a69ba8583dfbf7f5bec0ab1f93ce4c8ee1916eff44a93af5749c4`.
  With `ℓ = 440`, `ℓ + 1 + k ≡ 448 mod 512` gives `k = 7`, so the `1` bit, the
  zero run and the 64-bit length exactly fill the first block.
- **E2 — padding spills into a second block.** `Len = 448`, 56 bytes. `Msg`
  `2d52447d1244d2ebc28650e7b05654bad35b3a68eedc7f8515306b496d75f3e73385dd1b002625024b81a02f2fd6dffb6e6d561cb7d0bd7a`,
  `MD` `cfb88d6faf2de3a69d36195acec2e255e2af2b7d933997f348e09f6ce5758360`.
  `k = 511`; an implementation that computed the zero count as
  `448 − (ℓ + 1)` in `Nat` rather than modulo 512 truncates to zero here and
  loses the second block. This is the case `Impl.length_padBytes_eq` pins.
- **E3 — exactly one block of message, so padding is a whole extra block.**
  `Len = 512`, 64 bytes. `Msg`
  `5a86b737eaea8ee976a0a24da63e7ed7eefad18a101c1211e2b3650c5187c2a8a650547208251f6d4237e661c7bf4c77f335390394c37fa1a9f9be836ac28509`,
  `MD` `42e61e174fbb3897d6dd6cef3dd2802fe67b331953b06114a65c772859dfc1aa`.
  A `blocks` function that stopped when the remaining list was empty *before*
  appending the padding block, or one that emitted a spurious empty final
  block, is caught here and by nothing else in W1–E2.
- **E4 — the bit-order trap, and the one place FIPS 202 experience is
  actively misleading.** FIPS 180-4 §3.1 is **MSB-first within a word and
  within a byte**: *"within each word, the most significant bit is stored in
  the left-most bit position"*. FIPS 202 Appendix B.1 is **LSB-first within
  each byte** (`T[8i+j] = b_ij` with `h_i = Σ b_ij·2^j`). The two standards
  disagree, so foldlab's `formal/fips202` `bitsOfBytes` is **not** reusable
  here and must not be copied. A `bitsOfBytes` written to the FIPS 202
  convention passes `bytesOfBits_bitsOfBytes` and its converse — both
  round-trip lemmas hold for either convention — and fails only against a
  known-answer vector. W1 catches it; no structural theorem does.
- **E5 — the CAVP placeholder byte.** The `Len = 0` record of the vendored
  `.rsp` reads `Msg = 00`. That is one byte of hex text for a zero-length
  message, not a one-byte message: the file's own `Len` field is the
  authority and every other record's hex length is exactly `Len / 8` bytes
  (verified across all 65 records). A harness that read `Msg` and ignored
  `Len` would hash the single byte `0x00`, whose digest is
  `6e340b9cffb37a989ca544e6bb780a2c78901d3fb33738768511a30617afa01d`, not W1.
  The S1.4 runtime re-check of the vectors against the pinned file
  (`docs/SHA256-DAG.md` §8) must handle this record explicitly.

### Counterexamples to the strongest tempting overclaims

- **C1 — "the hash is injective."** False by pigeonhole: the domain is
  infinite and the codomain has 2²⁵⁶ elements. Injectivity appears nowhere in
  this lane, not even for `compress`. `pad` is injective as an encoding, and
  that is the only injectivity anything here may rely on; it is not stated as
  a §4 theorem and must not be quietly assumed by a bridge proof.
- **C2 — "the Lean `Spec` *is* FIPS 180-4."** Not a provable statement. The
  fidelity of a Lean transcription to an English-and-pseudocode standard is a
  named human-trust step. It is mitigated, not discharged, by: the pinned PDF
  digest; the section-by-section citation verification above; W1, W2, E1–E3
  from the pinned CAVP file; and the standard's own worked `"abc"` padding
  example. Every project in the surveyed prior art carries this same
  irreducible step. This contract states it rather than hiding it.
- **C3 — "the vectors passing means the implementation is correct."** 65
  short messages are finite evidence. They are not a theorem and they say
  nothing about the 56-to-64-byte boundary beyond E1–E3, nothing about large
  inputs, and nothing about `Fast`. The theorem that carries the claim is
  `Bridge.sha256_bridge`, and it carries it only for byte-aligned messages.
- **C4 — "two agreeing digest implementations means the bytes are right."**
  Refuted first-hand in this repository at P0 (`docs/PROVENANCE.md`, "Why the
  blob-hash check exists"): the in-tree SHA-256 and PowerShell `Get-FileHash`
  agreed on 8,401 bytes of EOL-converted `index.bs`, and the seal passed.
  Agreement of two hashes measures the same bytes twice. This is why the
  `.rsp` vendored at S1.0 was read from a git blob object, not a working tree.

### Assumptions, facts to prove, and deployment facts

**Assumptions (trusted, named).** Transcription fidelity of `Spec` to FIPS
180-4 (C2). The Lean v4.33.1 kernel, and the external rechecks that reduce
but do not remove reliance on it (`leanchecker`, lean4lean at S1.7). The
integrity of the two vendored files, resting on their sealed digests and, for
the `.rsp`, on the upstream git blob hash. The host and its hardware.

**Facts to prove.** Exactly the theorem list of §4 A1.S1–A1.S4 and no more:
the `Spec` length, padding and round-trip lemmas; the `Impl` length lemmas;
the seven bridge theorems with `Bridge.sha256_bridge` as their apex; the
`Fast` abstraction lemmas with `Fast.sha256_eq_impl` as theirs; the API
theorems `sha256_impl`, `sha256_spec`, `sha256_ofList`, and the `Digest`/`Hex`
facts. The obligation ledger below tracks them.

**Deployment facts (measured or tested, never claimed as theorems).** Wall
time and memory of every layer. Agreement with PowerShell `Get-FileHash` and
with the P0 tooling on real files. Byte-identical regeneration of
`generated/vendor-manifest.tsv` through the new implementation. Dual-host
agreement of axiom reports, compared as `(declaration, axiom-set)` pairs and
never as raw log lines.

### Claim-domain table

| Claim | Domain on which it is stated | Domain on which it is **not** stated |
| --- | --- | --- |
| `Bridge.sha256_bridge` | byte-aligned messages, `msg : List UInt8` | bit strings whose length is not a multiple of 8 |
